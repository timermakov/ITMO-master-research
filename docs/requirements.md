# Требования — система динамического прогрева сервисов (СДПС)

## Цель

Разработать и экспериментально оценить систему динамического прогрева микросервисов: новый инстанс прогревается зеркалированием боевого трафика с автоматическим наращиванием доли зеркалирования и переводом в активный режим по критериям готовности.

## Задачи исследования

1. Спроектировать архитектуру СДПС (warmkit, mirror-proxy, warmup-coordinator, benchmark).
2. Реализовать прототип библиотеки warmkit и интеграцию в LoadedService.
3. Построить стенд измерений с протоколами S0, S_ref, S_dw.
4. Экспериментально проверить гипотезы H1–H4.

## Функциональные требования

| ID | Требование |
|----|------------|
| FR-1 | mirror-proxy маршрутизирует боевой HTTP на активный инстанс и асинхронно зеркалирует GET на прогреваемый инстанс |
| FR-2 | warmup-coordinator наращивает долю зеркалирования и переводит инстанс в активный режим; единственный компонент, записывающий конфигурацию зеркалирования в ZK |
| FR-3 | warmkit ведёт FSM warmup-инстанса, регистрацию в ZK, готовность (`/readyz`), промежуточный обработчик теневого трафика |
| FR-4 | LoadedService имитирует "холодный" старт (ленивый hashmap) через `/work`, `/warmup` и `POST /reset` для независимых прогонов |
| FR-5 | benchmark выполняет протокол по benchmark-methodology.md (S0/S_ref/S_dw/H4): reset → прогрев → один контрольный запрос; без записи в ZK |

## Нефункциональные требования

| ID | Требование |
|----|------------|
| NFR-1 | Конфигурация только через `.env.local`; в коде — имена переменных, без числовых значений по умолчанию |
| NFR-2 | Асинхронное зеркалирование не блокирует ответ клиенту на активный инстанс (H4: накладные расходы ≤ 5%) |
| NFR-3 | Воспроизводимость: фиксированный WorkloadProfile, manifest.json, CV ≤ 20% по прогонам после фильтрации; READY_AFTER bench = warmup |

## WorkloadProfile

```json
{ "seed": "<int64>", "samples": "<int>" }
```

Единый профиль для S0, S_ref, S_dw и контрольного запроса T_first.

## Первичная метрика

**T_first** — `duration_ns` первого и единственного боевого `GET /work` (без теневого заголовка) после фазы прогрева в **независимом прогоне** (`POST /reset` перед каждым прогоном).

## Гипотезы

Сценарии: **S0** — "холодный" старт; **S_ref** — ручной `POST /warmup`; **S_dw** — динамический прогрев СДПС. Подробнее — `docs/benchmark-methodology.md`.

| ID | Смысл | Критерий выполнения |
|----|-------|---------------------|
| H1 | Динамический прогрев существенно быстрее холодного старта | P50(T_first) в S_dw ≤ P50(T_first) в S0 / 2 |
| H2 | Динамический прогрев не хуже эталона более чем в 2 раза | P50(S_dw) / P50(S_ref) ≤ 2,0 |
| H2_CI | H2 с учётом bootstrap-ДИ | Верхняя граница 95% ДИ для P50(S_dw) ≤ 2 × верхняя граница ДИ для P50(S_ref) |
| H3 | Готовность перед контрольным запросом в S_dw | `/readyz` = 200; FSM проходит «Registered» → «Ready» во всех валидных прогонах |
| H4 | Накладные расходы зеркалирования | P95 полной задержки через прокси при зеркалировании вкл. ≤ P95 при выкл. × 1,05 |

## Ограничения

- Теневое зеркалирование только для идемпотентных GET.
- Профилирование (pprof) на отдельном прогоне, не смешивать с T_first.
- ZooKeeper обязателен для полного стенда (docker-compose).
